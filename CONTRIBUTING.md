# Contributing to Aethera

Thank you for helping. Aethera is a self-hosted deployment platform (a Coolify alternative): a .NET control plane, a Go agent per server and a Next.js UI. This page is the short version; the details live in the documents it links to.

## Where to start

- [`docs/plan.md`](docs/plan.md) is the approved plan and the design system; [`docs/roadmap.md`](docs/roadmap.md) is the status; [`docs/architecture/`](docs/architecture/README.md) holds the decisions (ADRs) and an overview; [`docs/idea/01_AppIdea.md`](docs/idea/01_AppIdea.md) is the product spec.
- Read the ADR of the area you touch before changing it. A change that contradicts an ADR needs a new ADR (or an amendment) in the same pull request.
- [`CLAUDE.md`](CLAUDE.md) has the exact build and test commands and the rules for AI-assisted work; they apply to people too.

## Setting up

You need the .NET 10 SDK, Go 1.24, Node 22 with pnpm 10 and Docker. `buf` only when you change `proto/`.

```bash
docker compose -f deploy/docker-compose.dev.yml up -d      # PostgreSQL 17 and Redis 7 for the tests and the API

cd src/control-plane && dotnet build -warnaserror && dotnet test
cd src/agent && go vet ./... && go test ./... && make cross
cd src/web && pnpm install && pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

About 470 of the .NET tests need PostgreSQL (some also Redis) and are **skipped silently** without it, so a green `dotnet test` alone proves much less. Point them at a server whose role may `CREATE DATABASE` (each test class migrates and drops its own database):

```bash
export AETHERA_TEST_DB="Host=127.0.0.1;Port=5432;Username=aethera;Password=aethera;Database=postgres"
export AETHERA_TEST_REDIS=127.0.0.1:6379
```

CI runs everything with real service containers; your pull request must be green there.

End-to-end checks (they need Docker, and the browser one a Chrome or Edge):

| Command | Proves |
|---|---|
| `bash deploy/smoke.sh` | the web export, the API, PostgreSQL and the first-run flow |
| `E2E_PHASES=ui bash deploy/agent-e2e.sh` | the real agent, Docker-in-Docker, and the whole product UI in a browser (deploy, rollback, services, ops pages) |
| `bash deploy/install-e2e.sh` | `install.sh` on a throw-away host, the updater (update, failed pull, rollback), backups |

## Rules that are easy to break

- **API first.** The UI contains no logic the API lacks. A new screen starts with the endpoint.
- **Contracts are owned by the maintainers**: `proto/`, database migrations and the OpenAPI conventions change only when the issue says so. The OpenAPI document (`src/web/openapi/aethera.v1.json`) is generated by the .NET build and committed: build, then commit the diff; CI fails if it is stale. The TypeScript types come from it (`pnpm gen:api`).
- **The agent executes only typed, allowlisted commands.** Never add a way to run an arbitrary shell command on a server.
- **No secrets in logs, errors, test output or the audit log.** Secrets are encrypted at rest, masked in the UI, redacted from logs; a secret value leaves the API only through the audited reveal endpoint.
- **Tests are required** for new code (xUnit, `go test`, Vitest with Testing Library), and the build stays warning-free (`-warnaserror`). Fix a bug with a test that fails without the fix. Mocked tests are not enough for anything that crosses a boundary (the paging bug of Phase 4 passed every mocked test): run the matching end-to-end check.
- **The UI follows the design system** in `docs/plan.md` and `docs/design/`: dark by default, lime accent `#b8f26b`, mono labels, square corners, 1px borders, dotted-grid canvas. Components must be keyboard operable and labelled; the tests query by role and name.
- **Static export routing.** Detail pages are one shell per route (`/applications/_`); read the id with `useResourceId()` and link with `DetailLink` ([ADR 0005](docs/architecture/0005-web-routing.md)).
- **Dependency direction (.NET):** Api -> Infrastructure, Engine -> Domain; Domain depends on nothing. NuGet versions live only in `Directory.Packages.props`.

## Commits and pull requests

- [Conventional Commits](https://www.conventionalcommits.org/): `feat(api): ...`, `fix(agent): ...`, `docs:`, `test:`, `chore:`. Small logical commits; do not push to `master`.
- One pull request per change set; describe what changed, why, and how you verified it (the commands above, screenshots for UI changes: light and dark).
- Update [`CHANGELOG.md`](CHANGELOG.md) (under *Unreleased*) for anything a user or operator would notice, and the roadmap when a work package is done.
- Keep the diff focused: no drive-by reformatting.

## Reporting security problems

Please do not open a public issue for a vulnerability. Use GitHub's private vulnerability reporting on the repository (Security > Report a vulnerability). Describe the impact and how to reproduce it; we will answer there.

## Releases

Maintainers tag `vX.Y.Z` on `master`; the release workflow builds the images (GHCR, amd64 and arm64), the agent binaries and the release assets (see [ADR 0009](docs/architecture/0009-packaging-and-self-ops.md)). Move the *Unreleased* section of the changelog under the new version first; the workflow uses that section as the release notes. A manual run of the workflow is a rehearsal and publishes nothing.
