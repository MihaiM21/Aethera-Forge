# Release 0.2 — plan

Decided with the owner on 2026-10-30. R2 makes Aethera a multi-server platform: the second Turn One server (the old Coolify VPS, wiped) joins, builds can run on one server and the result on another, servers talk over a private mesh, and every pull request can get its own preview. Status lives in [`roadmap.md`](roadmap.md); R1 is [`release-0.1.md`](release-0.1.md); the design is [ADR 0012](architecture/0012-multi-server-mesh-previews.md).

## Decisions

| Area | Decision |
|---|---|
| Roles | `Master`, `Build`, `Storage`, `Worker` (existing enum; `Ci` stays unused). A server with **no roles accepts everything** (one-server installs never change). Applications are placed on `Worker` servers, databases and stateful services on `Storage` servers, builds on `Build` servers. Roles guide placement and are checked on create and move; they never stop a running workload. |
| Placement | Creating an application or service **without a server** picks one: eligible by role, enough unreserved memory, then the most free memory. The API answers why (`/placement/suggest`). Choosing a server by hand stays possible and wins. |
| Limits | CPU and memory limits and reservations already exist on workloads; R2 adds a **priority** (low / normal / high → CPU shares and OOM score) and makes all of it editable in a Resources tab that shows what is left on the server. |
| Capacity | A capacity view across servers: cores, memory, disk, live usage, and the sum of reservations and limits of what runs there, with an over-commit warning. |
| Build quota | Builds run in a **BuildKit builder container per server** (`aethera-buildkit`) with the server's build CPU and memory limits, on top of the existing `MaxConcurrentBuilds`. No quota set = the Docker daemon's builder, as today. |
| Build elsewhere | An application can name a **build server**. When it differs from the run server, the image travels through a **registry** configured in Aethera (GHCR, Docker Hub, a private registry): the build server pushes `<registry>/<namespace>/<slug>:<deployment id>`, the run server pulls it. The registry is chosen per build server (`buildRegistryId`), with a namespace on the registry. Rollbacks pull the same reference, so they work on any server. No registry = building elsewhere is refused with a clear message. Direct agent-to-agent transfer is not built. |
| Mesh | **WireGuard managed by the agent**: interface `aethera0`, one address per server from `10.210.0.0/16`, UDP 51820, full mesh, private keys generated on the server and never leaving it. **Tailscale option**: a server already on a tailnet uses its `tailscale0` address; Aethera does not run `tailscale up`. Off by default; turned on in Settings > Network. |
| Private-network deploys | A published port can bind to the **public** interface (today), the **private mesh address** or **loopback**. A database bound to the mesh is reachable from apps on other servers at `<mesh address>:<port>`, and never from the internet. Connection strings in the UI use the mesh address. |
| Previews | **GitHub and GitLab**, through the existing webhook endpoint (`pull_request`, `Merge Request Hook`). Opened / updated / reopened → deploy, closed or merged → tear down. Host `pr-<number>-<app host>` under the automatic domain base (wildcard or sslip.io). The preview URL is posted (and updated) as a **PR comment** when the git credential is a token. **Pull requests from forks are ignored unless allowed** per application (they would run untrusted code with the app's secrets). Preview-only environment variables override regular ones. A preview has its own containers, volumes and route, never the production ones. |
| Branch | `release-0.2`, stacked on `feat/coolify-style-deploys` (R1 is not merged yet). |
| If time is short | Drop priorities, then the Tailscale option, then PR comments on GitLab. **Build elsewhere, the mesh and GitHub previews are never cut.** |

## Work packages

Contracts first (orchestrator), then three packages in parallel worktrees with disjoint paths. Every package: tests required, warning-free builds, `/code-review`; `/security-review` for R2.2 (agent network changes) and R2.3 (webhooks running pull-request code).

- **R2.0 Contracts** (orchestrator): proto (`mesh.proto`: `MeshApply`, `MeshStatus`, `MeshRemove`; `BuildRequest.builder_limits`; `ResourceLimits.oom_score_adj`), domain fields and one migration (server build quota, build registry and mesh columns, registry namespace, application build server and preview settings, port bind scope, workload priority, preview variables, `previews` table, deployment preview and build server), .NET command records and mapper, seams (`IPlacementService`, `IPullRequestCommenter`), module stubs, web placeholders, ADR 0012.
- **R2.1 Multi-server placement & resources**: placement service and `/placement/suggest`, automatic server choice on create, move a workload to another server (redeploy there, volumes stay behind with a warning), priorities, build server + push to the build registry + pull on the run server (also for rollbacks), BuildKit builder with the build quota (agent), capacity API and view, server roles and quota editing in the UI, Resources tab.
- **R2.2 Secure networking**: agent WireGuard (`wgctrl`, kernel module, key generation, interface and peers, status), Tailscale address discovery, mesh settings, address allocation and `mesh.reconcile` job (on enable, server join, key or endpoint change), mesh status in heartbeat-driven server status and the UI (Settings > Network, server detail card), port bind scope in the plan builder and the UI, connection strings with mesh addresses, docs (firewall: UDP 51820).
- **R2.3 PR preview deployments**: webhook handling of pull/merge request events, preview lifecycle (create, redeploy on push, tear down on close, sweep of stale previews), plan builder naming (`<slug>-pr-<n>` containers, volumes and compose projects), preview routes, preview environment variables, PR comments (GitHub, GitLab), API and UI (application Previews tab, settings on the application).

`dotnet test` with Postgres/Redis, `go test` (and the agent's `-tags integration` WireGuard test on a Linux host with the module), `pnpm lint test build`, `deploy/smoke.sh`, `E2E_PHASES=ui deploy/agent-e2e.sh` extended with two agents: a build on one and the run on the other through a local registry, a mesh between them, a database bound to the mesh used from the other server, and a preview from a simulated pull request webhook. Then a PR `release-0.2` → `master` (after R1's), tag `v0.2.0-rc.1`, owner test with the second server, `v0.2.0`.
